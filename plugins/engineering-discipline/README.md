# Engineering Discipline

实验版 `0.2.0`。围绕三个检查：**Language**（含义是否一致）、**Structure**（知识和复杂性由谁承担）、**Evidence**（结论有什么证据）。维护当前知识，让任务有终点；不接管开发流水线。

## 使用

Claude Code 本地试用，在目标项目目录运行：

```bash
claude --plugin-dir /absolute/path/to/autoplug/plugins/engineering-discipline
```

显式入口使用完整插件命名空间，避免与其他插件重名：

- `/engineering-discipline:grill-design`：把影响实现的设计疑点变成已确认决策或明确阻塞；不自动生成 PRD 或开始开发。
- `/engineering-discipline:diagnose`：定位给定故障；只有用户同时授权修复才修改实现。
- `/engineering-discipline:tdd-slice`：显式选择 test-first 时使用，在已授权范围内逐片完成 red → green → refactor；不是所有开发任务的默认入口。

例如：`/engineering-discipline:grill-design 支持部分取消订单，先把行为边界讨论清楚，不写代码。`

其余三个是按需使用的参考原语，不默认出现在 Claude 命令菜单：

- `domain-language`：解决影响当前任务的含义歧义，维护词汇，不管理任务生命周期。
- `module-design`：检查调用者负担、知识归属和测试边界，按需更新当前架构或重要决策。
- `feedback-loop`：选择能区分对错的观察方法，真实执行，报告结果与缺口；仅在后续需要时保存专项证据。

每个 Skill 都可独立安装；流程已经内含所需规则，不要求加载原语或旧 Skill 才能继续。安装当前本地版本到目标项目，例如：

```bash
npx skills add /absolute/path/to/autoplug --skill tdd-slice -a codex
```

Codex 用 `$tdd-slice` 等名称显式选择。每个目录携带 `agents/openai.yaml`：三个流程关闭隐式调用，三个原语允许隐式调用。Claude 使用 `disable-model-invocation` 与 `user-invocable`。其他运行时可能不支持这些开关，正文仍要求显式进入流程；这些设置不是跨运行时的安全边界。

## 边界

- 不修改现有 Plugin，不依赖 `write-tests`，不接管 `auto-issue`。
- 没有 Hook、后台任务、专用 Agent 或权限扩张，不修改项目 `AGENTS.md`、`CLAUDE.md` 或配置来强制生效。
- 不硬性规定追问轮数、假设数量、候选设计数或第二个实现。
- 普通测试边界按现有契约选择，不设置用户审批仪式；新的产品行为、公共契约和难逆转决策仍要确认。
- 有文档写入授权时，维护相关知识；需要交接的工作保留当前任务快照，完成时收敛。无内容不建空文档，只读模式只提供拟议变更。
- 允许有噪声、视觉或人工反馈，但必须说明判据、实际观察和缺口。静态通过不等于行为改善。

## 项目知识与任务生命周期

**先发现、再复用。** 按项目指引和文档地图读取相关代码、当前契约、词汇、决策及活跃任务。兼容已有 `CONTEXT.md`、`docs/tasks/` 或外部 tracker，不强制改名、迁目录或生成另一套记录。没有约定时，只为实际需要确定最小位置，不要求 setup，也不自动修改 Agent 指令文件。

| 内容 | 职责 | 更新方式 |
|---|---|---|
| 领域词汇 | 概念含义与易混用称呼 | 在已有词汇表中维护当前定义；无词汇表时按需使用 `GLOSSARY.md` |
| 当前契约与架构 | 已实现的行为、职责、接口和不变量 | 原位更新所属契约、架构文档或 README；一个事实一个权威来源 |
| 重要决策 | 为什么选择它而不是其他方案 | 同时满足难逆转、脱离背景容易困惑、有真实替代方案时才写 ADR；遵守项目命名与保留政策 |
| 活跃任务 | 本次改变什么、还缺什么 | 维护范围、验收、确认选择及来源、未决问题、验证缺口和下一步；链接长期知识，不复制正文 |
| 专项证据 | 某版本在某环境实际验证了什么 | 仅为交接、比较、迁移或审计留存，包含版本、环境、结果、限制及可取回的产物 |

这些是内容分工，不是必建目录。三个显式工作流包含独立使用所需的生命周期规则；三个原语只维护各自负责的知识或证据，不重复承担整个任务的记录工作。

### 活跃任务是当前快照

一个有界变更需要跨会话交接时，复用它自己的任务；没有既有载体时才用 `.scratch/<slug>.md`。更新已有结论和状态，不追加每轮问答、“用户回复行”或反复覆盖旧状态的日期章节。后续新需求另立边界，不续写已经完成的任务。

已确认但未实现的设计仍是目标状态，保留在任务或 Proposed 决策中，不能改写成当前系统行为。已有确认不重问；假设、待审阅建议与实际观察分开表达。

### 完成意味着知识收敛

1. 将仍有效的知识更新到所属词汇、契约、架构或重要决策，并修正受影响的入口链接。
2. 保留有后续价值的证据。日常检查通常只需在回复里说明，不生成逐次运行报告。
3. 按项目政策关闭或删除临时任务与执行材料。没有政策时保留简短的已关闭任务，链接长期结果，不留下执行日记。

已提交的执行历史由版本控制保留；不得因此丢弃无关工作、必需审计材料或不可替代的证据。一次性数据迁移记录可以保留，但不应不断追加无关验证；旧测量不能改写为新版本的成功证明。ADR 是否保留 superseded 版本同样服从项目政策，不统一强制追加历史或删除旧 ADR。

### 授权与交接

“不写代码”不等于“禁止写文档”，但写入仍须在授权内；明确只读时仅给拟议更新并说明未保存。外部 tracker 写入另需授权，不能悄悄建立第二份权威记录。未运行的检查不标完成，旧证据不能直接证明当前代码。

换会话时给出活跃任务路径即可作为入口，例如“读取 `.scratch/team-space.md` 及其相关契约，继续已确认范围”。路径以项目实际约定为准；插件不提供自动恢复器，也不保证没有线索时找到正确任务。

## 日常使用

- **小修复或普通功能：** 直接描述需求，不必先选 Skill。没有长期知识变化或交接需求时，不额外建文档。
- **需要澄清的设计：** 用 `grill-design` 解决关键选择，并在允许写文档时保存可继续工作的设计快照。设计授权不会自动扩展为实现授权。
- **明确要求 test-first：** 用 `tdd-slice`。完整功能已经获授权时，切片是 Agent 内部执行方式，不应每完成一片就要求用户重新启动；遇到实质阻塞或用户指定边界才暂停。
- **复杂故障：** 用 `diagnose` 取得症状敏感的证据并在授权内修复；暂停时保存未决原因与下一步探测，解决后收尾，不保留逐次探测流水。

纯重构可使用已有通过的行为基线，视觉改动可使用浏览器观察；不为了使用插件而制造一次 red。各流程不自动调用其他工作流、不接管 issue 到 PR 的编排。

## 维护与验证

仓库根目录执行打包校验：

```bash
uv run --with PyYAML==6.0.3 python -m unittest discover -s tests -v
```

这些检查覆盖清单、YAML/JSON、调用策略、独立分发路径及文档入口，**不评估模型行为**，也不锁定正文措辞或要求六个 Skill 复制同一段规则。

行为检查使用隔离样例，旧版与新版处理相同输入，观察实际产物：

- 小修复：行为正确且没有新增无用任务、ADR、词汇表或验证报告。
- 跨会话设计：既有确认不重问，任务成为当前快照，目标行为没有冒充已实现契约。
- 功能收尾与演进：当前契约更新、旧任务结束、新需求独立保存，必要迁移证据不丢失。

样例检查不证明长期效果、隐式触发准确率或所有运行时兼容性；仍需在真实项目中观察返工、追问与文档维护成本。评估产物放在独立验证目录，不追加到项目任务或当前架构文档。

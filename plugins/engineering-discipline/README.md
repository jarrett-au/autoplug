# Engineering Discipline

实验版 `0.3.0`。围绕三个检查：**Language**（含义是否一致）、**Structure**（知识和复杂性由谁承担）、**Evidence**（结论有什么证据）。文档服务于下一次正确行动，不用于证明上一次做了多少工作；不接管开发流水线。

## 使用

Claude Code 本地试用，在目标项目目录运行：

```bash
claude --plugin-dir /absolute/path/to/autoplug/plugins/engineering-discipline
```

显式入口使用完整插件命名空间，避免与其他插件重名：

- `/engineering-discipline:project-context`：显式建立、整理或校准项目上下文；既有项目核对现状并收敛，新项目只保存已确认信息，结构合理时可以不改。
- `/engineering-discipline:grill-design`：把影响实现的设计疑点变成已确认决策或明确阻塞；不自动生成 PRD 或开始开发。
- `/engineering-discipline:diagnose`：定位给定故障；只有用户同时授权修复才修改实现。
- `/engineering-discipline:tdd-slice`：显式选择 test-first 时使用，在已授权范围内逐片完成 red → green → refactor；不是所有开发任务的默认入口。

例如：`/engineering-discipline:grill-design 支持部分取消订单，先把行为边界讨论清楚，不写代码。`

其余三个是按需使用的参考原语，不默认出现在 Claude 命令菜单：

- `domain-language`：解决影响当前任务的含义歧义，维护词汇，不管理任务生命周期。
- `module-design`：检查调用者负担、知识归属和测试边界，按需更新当前架构或重要决策。
- `feedback-loop`：选择能区分对错的观察方法，真实执行，报告结果与缺口；取得证据不等于生成证据文档。

每个 Skill 都可独立安装；流程已经内含所需规则，不要求加载原语或旧 Skill 才能继续。安装当前本地版本到目标项目，例如：

```bash
npx skills add /absolute/path/to/autoplug --skill tdd-slice -a codex
```

Codex 用 `$project-context`、`$tdd-slice` 等名称显式选择。每个目录携带 `agents/openai.yaml`：四个流程关闭隐式调用，三个原语允许隐式调用。Claude 使用 `disable-model-invocation` 与 `user-invocable`。其他运行时可能不支持这些开关，正文仍要求显式进入流程；这些设置不是跨运行时的安全边界。

## 边界

- 不修改现有 Plugin，不依赖 `write-tests`，不接管 `auto-issue`。
- 没有 Hook、后台任务、专用 Agent 或权限扩张，不修改项目 `AGENTS.md`、`CLAUDE.md` 或配置来强制生效。
- 不硬性规定追问轮数、假设数量、候选设计数或第二个实现。
- 普通测试边界按现有契约选择，不设置用户审批仪式；新的产品行为、公共契约和难逆转决策仍要确认。
- 有文档写入授权时，维护相关知识；需要交接的工作保留当前任务快照，完成时收敛。无内容不建空文档，只读模式只提供拟议变更。
- 允许有噪声、视觉或人工反馈，但必须说明判据、实际观察和缺口。静态通过不等于行为改善。

## 当前知识的组织

先读取当前需求、相关代码、有效契约和项目指引。只有具体问题无法由现状回答时，才查相关提交或历史材料；不要求重读实现过程来理解系统。已有约定优先，不改名已有 `CONTEXT.md` 或强制搬迁文档。

默认先更新已有章节。只有独立、稳定的阅读问题或更新边界才值得拆文件；新增功能、篇幅变长或“以后可能有用”都不足以独立成文。当前定义原位更新，一个事实一个权威来源，其他地方只保留必要提示与链接。

没有既有约定、又确实有内容需要独立保存时，可采用：

| 位置 | 保存什么 |
|---|---|
| `README.md` | 使用、运行、验证入口与简短文档导航 |
| 已有 `AGENTS.md` / `CLAUDE.md` | 项目约束与阅读指引；仅明确授权维护指引时编辑 |
| `GLOSSARY.md` / 已有 `CONTEXT.md` | 易混淆的领域概念，不放操作步骤、字段清单或进度 |
| `docs/architecture/overview.md` | 当前职责、数据流与跨模块约束，不抄代码清单 |
| `docs/architecture/client-contract.md` | 调用者需要遵守的契约，不按 Case、Provider 等功能各拆一份 |
| `docs/adr/` | 重要且仍有解释价值的决策与真实取舍 |

这是按需使用的位置建议，不是必建骨架；小项目只有 README 也可以，内部库未必需要独立客户端契约。不创建空目录、索引、模板、`evidence/` 或验证总账。已有结构合理时直接复用，不要求 setup。

ADR 的门槛是难逆转、脱离背景容易困惑且存在真实替代方案。满足门槛且获得文档写入授权时应主动记录，不把理由全部塞进架构，也不为普通实现细节写 ADR。只记录问题、约束、决定、真实替代方案与代价；字段和当前操作规则链接其权威文档，不记录讨论轮次，不编造批准日期。遵守项目对旧 ADR 的保留政策，失效决定不作为当前默认依据。

## 活跃任务与完成

未完成工作确需跨会话交接时，复用对应 tracker；没有约定时才用 `.scratch/<slug>.md`。任务只保留当前范围、验收、已确认选择及来源、未决问题、验证缺口和下一步。批准但未实现的行为仍是目标，不得写成当前能力。

每次涉及知识变化时，在当前范围内收尾：

1. 找到所属文档并原位更新，替换过时内容。
2. 删除本次范围内的重复说明，修复受影响链接；不发动全仓库文档审计。
3. 有效知识归位后，移除本次已完成的本地任务，不保留 closed 占位文件或另建归档。显式项目保留政策优先；外部 tracker 仅在授权内关闭，不删除其历史。

新需求另立边界，不续写已完成任务。保留无关用户工作、真实备份、数据、图片与明确要求留存的原始材料；清理总结性 Markdown 不授予删除这些对象的权限。

## 验证结果与历史材料

默认在回复或当次交付中报告实际验证及限制，不自动落成长期文档。做过迁移、比较或调试本身不是留档理由，也不为删日志再建设归档体系。

只有明确审计/保留要求，或具体未决调查、活跃交接确实需要材料时才保存，并明确用途、范围、版本/环境和取回方式；不默认为项目上下文的一部分。旧检查通过不能证明新代码正确；缺少材料时说明缺口，不伪造恢复或默认为通过。

## 项目约定与授权

Skill 复用项目已有的位置、权威与保留规则，不静默写入 Agent 指令或扩大权限。用户明确授权维护项目指引时，将相关规则更新到已有位置，不另建一份重复政策；这不是必跑安装步骤。未加载 Skill 的会话不会因插件存在而自动获得这些规则。

“不写代码”不等于“禁止写文档”，但明确只读时只给拟议更新并说明未保存。外部写入另需授权，不在无权限时悄悄建立第二份权威 tracker。换会话时给出实际活跃任务路径；插件不提供无上下文自动恢复器。

## 建立或整理项目上下文

`project-context` 是首次接手、上下文明显失序或重大结构变化时的显式入口，不是每次开发的前置步骤，也不自动启动 `grill-design` 或实现流程。

```text
/engineering-discipline:project-context
整理当前项目的上下文与文档。允许更新已有项目级 AGENTS.md；
不修改产品代码、运行配置、数据、图片或备份。
```

只读评估时明确“只讨论，不修改任何文件”。普通文档整理不自动授权修改 Agent 指引；未获授权的指引变更只在回复中提出，不另存一份政策。沿用目标运行时的现有入口，不同时生成重复的 AGENTS.md/CLAUDE.md，不改全局 harness 设置。

已有项目先核对代码、契约、命令与已知部署边界，再确定知识归属、执行收敛并检查链接。checkout 不代表线上版本；已发布契约、运维/回滚说明和审计材料不能按流水账清除。清理授权不包含真实数据或原始产物删除。

新项目只保存已确认的目标、约束、必要词汇和真实未决问题。栈与接口未定时，不虚构构建命令、架构或 API，不生成空目录。下一轮可把活跃任务交给 `grill-design` 澄清；已实现后再更新当前契约。

重复运行不应为追求统一格式重新改名、排序或改写合理文档。完成报告只说明实际变更、入口、检查与阻塞，不创建永久“整理报告”。本入口独立工作，不依赖 deprecated 的 `codebase-rules-generator`。


## 日常使用

- **小修复或普通功能：** 直接描述需求，不必先选 Skill。没有长期知识变化或交接需求时，不额外建文档。
- **需要澄清的设计：** 用 `grill-design` 解决关键选择，并在允许写文档时保存可继续工作的设计快照。设计授权不会自动扩展为实现授权。
- **明确要求 test-first：** 用 `tdd-slice`。完整功能已经获授权时，切片是 Agent 内部执行方式，不应每完成一片就要求用户重新启动；遇到实质阻塞或用户指定边界才暂停。
- **复杂故障：** 用 `diagnose` 取得症状敏感的证据并在授权内修复；暂停时保存未决原因与下一步探测，解决后收尾，不保留逐次探测流水。

纯重构可使用已有通过的行为基线，视觉改动可使用浏览器观察；不为了使用插件而制造一次 red。各流程不自动调用其他工作流、不接管 issue 到 PR 的编排。

## 维护与验证

仓库根目录执行打包校验：

```bash
uv run --with PyYAML==6.0.3 python -m unittest discover -s tests -v
```

这些检查覆盖清单、YAML/JSON、调用策略、独立分发路径及文档入口，**不评估模型行为**，也不锁定正文措辞或要求各 Skill 复制同一段规则。

行为回归输入见 [evals/evals.json](evals/evals.json)，不是 Skill 运行时依赖。将其中初始文件写入隔离目录，按阶段处理同一项目；`fresh_session` 阶段换执行者，只交接当前文件，不传上一轮聊天。旧版与新版从相同输入分别运行，保留阶段产物在仓库外供比较：

- 连续设计、实现、改变行为、修 bug、删除功能：既有章节是否原位更新，旧任务是否退出，是否出现按功能拆文档或验证总账。
- 真实取舍是否产生有价值的 ADR，普通局部选择是否避免文档仪式。
- 明确审计要求和只读限制是否仍被遵守，原始数据/备份是否未受清理影响。
- `project-context` 的独立场景见 [上下文回归输入](skills/project-context/evals/evals.json)：存量项目保护已发布契约，新项目不虚构事实，随后换执行者再次整理以检查是否稳定。
- [混合历史回归](skills/project-context/evals/mixed-history.json)：先提炼当前契约再处置旧记录，保护有实际恢复依赖的历史原文；不为全局链接全绿修缮历史。另由只读新执行者从当前入口回答行为问题，不把链接存在当作理解正确。

这些场景检查文档演进而不是文件越少越好。打包校验不证明行为改善，少量模拟执行也不证明长期效果、隐式触发准确率或所有运行时兼容性。

## 设计来源

参考 Matt Pocock 的 [engineering skills](https://github.com/mattpocock/skills/tree/main/skills/engineering) 中 grilling、grill-with-docs、domain-modeling、codebase-design、diagnosing-bugs 和 tdd 的问题意识。本插件独立重写，不要求使用上游或 Autoplug 旧版测试 Skill；尤其不沿用固定假设配额、强制第二 adapter 或所有 seam 均需审批的规则。
